# WP-0.3 --- Runner Lifecycle Implementation / Remediation

**Project:** ThisByte Action Runner\
**Role:** Implementation Tool\
**Predecessor:** WP-0.2 --- Runner Lifecycle & Registration Design ---
**APPROVED 2026-10-12**\
**Objective:** Implement the approved persistent-runner lifecycle
architecture and remediate LIFE-4/LIFE-5 without registering the runner
or introducing credentials.

------------------------------------------------------------------------

## 1. Purpose

WP-0.3 implements the Owner-approved WP-0.2 lifecycle design baseline.

The implementation must preserve the central WP-0.2 model:

-   Registration/configuration state is persistent and sensitive.
-   Bootstrap registration is explicit.
-   Normal shutdown never deregisters the runner.
-   Restart reuses persisted runner identity.
-   Invalid or incomplete state fails closed.
-   Permanent removal is a separate administrative operation.
-   Silent `--replace` behavior is prohibited.
-   Automatic registration loops are prohibited.

This work package remains subject to the existing runner-registration
hold.

------------------------------------------------------------------------

## 2. Implementation Requirements

### 2.1 State-Aware Entrypoint

Refactor `entrypoint.sh` into a state-aware lifecycle.

Startup behavior shall be:

1.  Detect valid persisted runner configuration.
2.  If valid configuration exists, start the listener.
3.  If configuration is absent, fail closed unless explicit bootstrap
    mode is requested.
4.  If bootstrap is requested but the required runtime registration
    token is absent, fail closed.
5.  Registration failure must stop execution and preserve actionable
    diagnostics.

WP-0.3 shall not perform an actual registration.

### 2.2 Resolve LIFE-4: No Deregistration on Normal Shutdown

Eliminate deregistration-on-shutdown behavior.

The following events must terminate the listener cleanly without
executing GitHub runner removal:

-   `SIGTERM`
-   `SIGINT`
-   `docker stop`
-   Docker Desktop shutdown
-   WSL2 shutdown
-   Windows shutdown

The expected persistent-runner state after a normal shutdown is
registered but Offline.

Normal shutdown and permanent deregistration must remain separate
lifecycle operations.

### 2.3 Persistent Registration and Configuration State

Implement explicit persistent storage for runner identity and
configuration generated by `config.sh`.

Requirements:

-   Registration/configuration state survives container recreation.
-   Persistence does not depend accidentally on `_work`.
-   Registration/configuration state is treated as sensitive
    credential-bearing material.
-   Storage boundaries are explicit and documented.

### 2.4 Separate `_work` from Runner Identity

Implement the approved disposable-by-default `_work` model unless
implementation reveals a documented technical constraint requiring
architecture review.

Requirements:

-   `_work` must not be used as a substitute for
    registration/configuration persistence.
-   Runner identity/configuration persistence and job workspace
    persistence must remain separate concerns.
-   Future performance requirements may use explicit GitHub caching or
    artifacts rather than relying on workspace persistence.

### 2.5 Bootstrap Mechanism Without Registration

Implement the mechanism required for explicit first-time bootstrap
without performing bootstrap.

The implementation may support accepting a short-lived repository runner
registration token at runtime.

WP-0.3 must not obtain, generate, store, or use a real registration
token, and must not introduce a long-lived PAT.

`RUNNER_TOKEN` must not become permanent `.env` configuration.

Ordinary runner restarts must not require a registration token.

### 2.6 Runner Version Control

Registration/configuration logic shall use `--disableupdate`.

The Docker image remains the authoritative runner-version boundary.
Runner upgrades shall occur through deliberate image-version changes
rather than self-update by the running container.

### 2.7 Partial and Invalid State Handling

Implement fail-closed handling for damaged, incomplete, inconsistent, or
ambiguous runner configuration state.

The implementation must not automatically register, deregister, delete
state, replace a GitHub runner, or attempt destructive recovery.
Instead, emit actionable diagnostics and stop.

### 2.8 Stale and Duplicate GitHub Runner Records

Do not silently resolve stale or duplicate GitHub runner records.

Automatic use of `--replace` is prohibited.

GitHub/local-state disagreement remains an explicit administrative
recovery condition.

### 2.9 Explicit Decommission Path

Implement an explicit runner decommission/removal path, but do not
execute it during WP-0.3.

Requirements:

-   Decommission is distinct from normal shutdown.
-   Decommission requires intentional operator action.
-   Ordinary lifecycle events cannot accidentally enter decommission
    behavior.
-   Local state removal and GitHub deregistration are controlled
    administrative operations.

### 2.10 Restart Policy

Review the current `restart: unless-stopped` behavior.

It may be preserved only if the revised fail-closed lifecycle prevents
registration/configuration failures from becoming destructive,
credential-consuming, or uncontrolled retry loops. Failed bootstrap or
invalid-state conditions must remain diagnosable.

## 3. Required Local Validation

WP-0.3 shall execute all validation that can safely be performed without
GitHub runner registration.

Required local validation includes:

-   Docker Compose configuration validation.
-   Docker image build.
-   Non-root execution verification.
-   Verification that privileged mode is not enabled.
-   Verification that the Docker socket is not mounted.
-   Verification that unnecessary inbound ports are not exposed.
-   Startup with no registration state.
-   Explicit bootstrap request with no registration token.
-   Malformed or partial registration-state behavior where safely
    reproducible.
-   Signal and shutdown handling that does not invoke deregistration.
-   Persistence/storage configuration inspection.
-   Static verification that no secret or credential has been
    introduced.

Tests requiring a genuinely registered GitHub runner must be marked
**DEFERRED**, not PASS.

Deferred registered-runner testing includes actual GitHub Online/Offline
transitions; reconnect after Docker, Docker Desktop, WSL2, or Windows
restart; recovery after abnormal host termination; stale GitHub-record
handling against GitHub; controlled decommission; controlled
re-registration; and execution of a harmless GitHub Actions CI job.

  ID                                  Acceptance Criterion
  ----------------------------------- -----------------------------------
  AC-01                               Normal shutdown cannot deregister
                                      the runner.

  AC-02                               Valid persisted configuration
                                      starts the listener without a
                                      registration token.

  AC-03                               Missing state without explicit
                                      bootstrap fails closed.

  AC-04                               Explicit bootstrap without a token
                                      fails closed.

  AC-05                               Registration token is
                                      bootstrap-only and is not persisted
                                      as normal configuration.

  AC-06                               Registration/configuration state
                                      has an explicit persistent storage
                                      boundary.

  AC-07                               `_work` is separated from
                                      persistent runner
                                      identity/configuration.

  AC-08                               Partial or invalid state fails
                                      closed with actionable diagnostics.

  AC-09                               No automatic `--replace` or silent
                                      stale-runner remediation exists.

  AC-10                               Explicit decommission is separate
                                      from normal shutdown.

  AC-11                               Registration/configuration uses
                                      `--disableupdate`.

  AC-12                               Restart policy cannot cause an
                                      uncontrolled registration loop.

  AC-13                               Existing security controls remain
                                      intact: non-root execution, no
                                      privileged mode, no Docker socket,
                                      no unnecessary inbound ports, and
                                      no baked credentials.

  AC-14                               Docker Compose validation and
                                      Docker image build succeed.

  AC-15                               Registered lifecycle tests that
                                      cannot yet be executed are
                                      explicitly marked DEFERRED.

  AC-16                               Implementation handoff provides
                                      traceable evidence for AC-01
                                      through AC-15.

## 5. Required Evidence and Handoff

The Implementation Tool must provide one-to-one evidence for every
acceptance criterion. Unsupported registered-runner tests must be
explicitly marked **DEFERRED**.

The implementation handoff shall be placed under `_Context/Executions/`.

The handoff shall identify:

-   Files changed.
-   Commands executed.
-   Actual command/test results.
-   Acceptance-criterion disposition.
-   Remaining deferred tests.
-   Security observations.
-   Any architecture or governance conflict discovered during
    implementation.
-   Any condition requiring Owner or Chief Architect review.

Unsupported assertions must not be reported as PASS.

work package, local non-credentialed testing, lifecycle changes required

-   Creating deployment SSH credentials.

-   Modifying the `thisbyte-website` repository or its GitHub workflows.
-   Creating production deployment workflows.
-   Adding deployment credentials.
-   Performing a deployment.
